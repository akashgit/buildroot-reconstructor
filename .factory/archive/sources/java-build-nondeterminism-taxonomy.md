# Non-Determinism Sources in Java Builds — Ranked by Frequency

Essential reference for Level 4 comparison pipeline: which JAR elements produce false-positive diffs and how to handle each.

## Ranked Sources

| Rank | Source | Location | Handling |
|------|--------|----------|----------|
| 1 | ZIP entry timestamps | All entries | Compare entry names/sizes, ignore timestamps |
| 2 | `Build-Jdk` / `Built-By` / `Created-By` in MANIFEST.MF | META-INF/MANIFEST.MF | Strip these fields before comparison |
| 3 | `Bnd-LastModified` (OSGi bundles) | MANIFEST.MF | Strip before comparison |
| 4 | File ordering within JAR | ZIP directory | Sort entries by name before comparison |
| 5 | `.properties` file timestamps | `java.util.Properties.store()` output | Strip comment lines starting with `#` |
| 6 | Constant pool ordering in `.class` | Bytecode | Use CFR decompiler, not raw javap |
| 7 | `pom.properties` timestamp comment | META-INF/maven/ | Strip `#Generated by` comment line |
| 8 | `git.properties` (Spring Boot) | git.properties in JAR | Strip or compare only `git.commit.id` |
| 9 | Compression level differences | ZIP metadata | Compare uncompressed content, not compressed bytes |
| 10 | Locale/encoding differences | Java <=17 builds | Not controllable at comparison time |

## Key Insight
Timestamps are the dominant source (rank 1-3, 5, 7). The comparison pipeline should normalize all timestamp-bearing fields before any semantic comparison. This aligns with Google OSS-Rebuild's `stabilize` tool philosophy: identify "non-semantic" elements and strip them.

## Implications for Verdict Taxonomy
- **IDENTICAL**: SHA-256 match (no non-determinism at all — rare)
- **EQUIVALENT**: All differences are in the list above — functionally identical builds
- **DIVERGENT**: Differences outside this list — actual code/resource changes
- **FAILED**: Build or download failure
