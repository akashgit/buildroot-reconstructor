# Build-Jdk-Spec vs Language Level — JDK Inference Gap

## Finding

The JDK resolver picks the *language level* (source/target) not the *actual build JDK*. These can differ significantly — a project can cross-compile to Java 8 bytecode using JDK 21.

## Impact Table

| Package | Inferred JDK (source/target) | Actual Build-Jdk-Spec | Would build? |
|---------|------------------------------|----------------------|-------------|
| commons-lang3 | 8 (maven.compiler.source) | **21** | NO — plugins need JDK 11+ |
| spring-boot | 8/17 (CI) | 8 (1.8) | YES |
| spring-core | 8/17 (CI) | N/A | UNCERTAIN |
| thymeleaf-spring5 | 8 (default) | **11** | NO |

## Root Cause

The 12-source priority heuristic resolves `maven.compiler.source=1.8` → JDK 8. But commons-lang3 is actually built with JDK 21. The Containerfile gets `FROM eclipse-temurin:8-jdk`, which lacks APIs/plugins that require JDK 11+.

## Fix: Priority 0 Signal

The `verify` command already reads `Build-Jdk-Spec` from the JAR manifest. Feed this back into the JDK resolver as the highest-priority signal (Priority 0, above CI setup-java at Priority 1).

**Revised hierarchy:**
0. Build-Jdk-Spec from published JAR manifest (OBSERVED — actual build environment)
1. CI setup-java (OBSERVED — intended build environment)
2-12. (existing signals)

## Research Grounding

BuildGen paper key insight: "Build outputs generally depend on the major version of the JDK used to compile — even with source/target defined, each major JDK version changes the generated bytecode."
